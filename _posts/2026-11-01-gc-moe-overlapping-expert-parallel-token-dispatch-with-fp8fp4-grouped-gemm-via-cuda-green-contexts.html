GC-MoE: Overlapping Expert-Parallel Token Dispatch with FP8/FP4 Grouped GEMM via CUDA Green Contexts

速读

一句话结论 面向 NVIDIA Hopper 与 Blackwell GPU，GC-MoE（一种开源低精度混合专家推理算子）借 CUDA Green Contexts（驱动级流多处理器 SM 静态划分机制）将跨卡 token 分发与 FP8×FP4 分组矩阵乘拆到独立 SM 分区并发执行，在精度对齐前提下，于 8 卡 H20 和 8 卡 B300 全部 54 个解码测试点平均提速 1.106–1.188 倍、最高 1.353 倍。

要解决什么问题 专家并行（EP，各卡分持部分专家并跨卡路由 token）的解码阶段每卡单层仅处理 1–256 个 token，单个本地专家有效行数极少，分组矩阵乘受限于高带宽显存 HBM 的权重流式读取与小批量发射延迟，并不缺张量核心算力；而跨卡全对全分发受限于通信延迟与原子计数，少量 SM 即可打满卡间互联 NVLink。现有最优方案 DeepGEMM 的 Mega MoE（单核持久化融合算子）把分发、分组矩阵乘与合并塞进同一核函数，靠每颗 SM 内不同线程束共享资源实现通信与计算重叠，但卡在三个机制上：一是分发线程束及中转缓冲侵占每颗 SM 的寄存器与共享内存，计算线程束始终无法独占整颗 SM；二是同步域覆盖全卡（B300 共 148 个 SM），序言和尾部网格同步必须等待最慢线程块，且每次重放清理工作区后还要多付一次跨卡 tag-2 屏障才能复用缓冲，关键路径为

$$T_{\mathrm{mega}} = t_{\mathrm{pro}} + \max\left(T_{\mathrm{pull}}^{\mathrm{shared}}, T_{\mathrm{gemm}}^{\mathrm{shared}}\right) + \max\left(T_{\mathrm{combine}}, t_{\mathrm{clean}} + t_{\mathrm{tag2}}\right)$$


当合并耗时短于清理加屏障时，跨卡往返延迟直接暴露；三是所有阶段绑死在同一线程块预算内，难以单独调优。常规多 CUDA 流并发又缺硬件隔离，全卡核函数仍会互抢 SM。

怎么做的 核心思路是利用解码期计算受带宽而非算力限制的特点，借 CUDA Green Contexts 在驱动层把 GPU 静态切为小通信分区与大计算分区（B300 的 148 个 SM 经驱动对齐切为 20 与 128，H20 默认请求 4 个通信 SM），并开启并发上限为 1 的平衡工作队列避免两上下文隐式串行。分发与计算由此成为独立核函数，独享寄存器、共享内存和更小同步域，同时绕开上述三处卡点。单层基于对称内存（多卡可经 NVLink 远程直访的统一显存区）组织为三节点 CUDA Graph（预录制核函数依赖以省去主机发射开销的计算图；Hopper 融合共享专家时增为四节点）：分发节点 Role1 在通信分区统计并原子发布各专家 token 数，经持久化 tag-1 屏障后拉取远端 FP8 激活、缩放因子与路由元数据，写入按每块 $B_M$ 个 token 循环复用的令牌环；计算节点 Role2 作为并发图根节点在计算分区执行 FP8 乘 FP4 分组矩阵乘，第一层尾声融合门控激活 SwiGLU、路由加权与 FP8 重量化，第二层尾声将 BF16 部分和直接分散写回源卡合并缓冲，且可将 FP8 共享专家零拷贝并入同一任务流；收尾节点 Role3 依赖前两者，前 4 个线程束并发处理账务与状态重置，其余线程束规约 top-$k$ 与共享专家输出。跨分区协同依赖两项机制：一是带代际号 $g$ 的块级令牌环握手与 64 位完成位图，按单卡容量 $T_{\max}$、卡数 $P$、路由数 $k$ 和单卡专家数 $e$ 设逻辑块池规模为 $N_{\mathrm{pool}} = \lceil T_{\max} \cdot P \cdot \min(k, e) / B_M \rceil + e$，当环块计数满足

$$\mathrm{l1\_full\_count} = B_M \cdot (g + 1)$$


时 Role2 立即启动该块第一层计算，第二层按位图等待对应两个输出瓦片，无需等分发全部结束；二是奇偶双缓冲的每专家接收计数（第 $N$ 次重放消费 $N \bmod 2$ 代），Role3 网格同步后翻转奇偶位，由 tag-1 屏障与合并就绪信号链保序，彻底去除尾部跨卡 tag-2 屏障，且所有同步状态常驻设备端支持无主机干预重放。两代架构计算各自特化：Blackwell（SM103）用操作数互换的双线程块硬件块缩放指令 tcgen05（同一指令兼容 FP4 路由与 FP8 共享权重），并新增 K128 瓦片连续预打包，让异步张量内存加速器 TMA 单次突发读完一块权重；Hopper（SM90）无原生 FP4 矩阵乘，离线做专家级窗口重缩放与通道重排，核内寄存器将 FP4 解码为 E4M3 后发射线程组异步矩阵乘指令 WGMMA，并在其外按每 32 维施加缩放。

效果如何 实验在 8 卡 H20 与 8 卡 B300 上经 NVLink 对称内存和 CUDA Graph 重放评测两个生产级混合专家层：GLM-5.2（隐藏维 6144、中间维 2048、256 专家、top-8、1 个共享专家，测于 B300）与 DeepSeek-V4.1-Flash（隐藏维 5120、中间维 2304、384 专家、top-6、1 个共享专家，测于两平台），每卡扫描 1–256 个 token。对比基线为代表"单核共享 SM 重叠"路线的 DeepGEMM Mega MoE：B300 上用官方融合核（含融合共享专家模式，功能对齐）；H20 上因官方未开源 SM90 内核，对比作者按相同单核设计移植的参考核，共享专家场景则对比路由核加独立共享专家核的非融合基线。GC-MoE 在全部 54 个测试点上均领先：8 卡 H20 上纯路由与共享专家套件平均加速均为 1.188 倍，峰值分别达 1.296 倍（每卡 16 个 token）和 1.353 倍（每卡 8 个），每卡 4–32 个 token 区间延迟降低 20.9%–22.8%；8 卡 B300 上即便计算分区让出 20 个 SM 仅留 128 个，纯路由仍平均提速 1.106 倍（GLM-5.2 为 1.102 倍，DeepSeek-V4.1-Flash 为 1.109 倍，峰值 1.189 倍），融合共享专家平均提速 1.123 倍（GLM-5.2 为 1.131 倍，DeepSeek-V4.1-Flash 为 1.115 倍，峰值 1.209 倍，出现在每卡 1 个 token）。数值精度与基线匹配，两平台相对 BF16 参考余弦相似度均不低于 0.97，H20 上与基线最小余弦 0.9999997 且纯路由最大误差完全一致。局限在于：算子面向解码优化，大批量或预填充时计算分区成为瓶颈，每卡 256 个 token 时加速收窄至 1.01–1.13 倍；H20 共享专家融合内部消融平均仅快 1.031 倍，每卡 32–128 个 token 时因任务排在路由之后反略慢（0.973–0.985 倍）；硬设计限制中间维不超过 4096 且为 128 倍数、隐藏维为 256 倍数、路由与共享专家槽位总和不超过 32、总专家数不超过 2048、卡数不超过 72 且单工作区调用须串行；此外当前版本未提供分区 SM 数量与重叠开关的受控消融实验。

一、核心问题与主要贡献

1.1 研究背景与核心痛点

混合专家（Mixture-of-Experts, MoE）架构已成为大语言模型（LLM）在不按比例增加推理计算量的前提下扩展参数规模的主流范式。在生产环境服务中，MoE 层普遍采用专家并行（Expert Parallelism, EP）进行切分：每张 GPU 仅持有部分专家，每一层都需要执行全对全（all-to-all）的 Token 分发（dispatch）、本地路由专家的分组矩阵乘（grouped GEMM）计算，以及将部分输出规约回源 Rank 的聚合（combine）操作。在交互式推理中，Decode（解码）阶段主导了服务开销；在此阶段，每个 Rank 通常仅处理 1–256 个 Token。在这种极小批量下，MoE 层并非受限于 Tensor Core 算力（compute-bound），而是由跨 Rank 的 Token 传输延迟以及从 HBM 流式读取量化专家权重的显存带宽（bandwidth-bound）所主导。

针对这一开销结构，算子级优化已收敛至融合持久化内核（fused persistent kernel），以 DeepGEMM 的 Mega MoE 为 Blackwell（及参考移植版 Hopper）上的最先进代表。然而，Mega MoE 的通信与计算重叠是通过在每一个 SM（Streaming Multiprocessor）内部共享资源实现的：每个 SM 内有 4 个分发 Warp 与 2 个 TMA 加载 Warp、1 个 MMA 发射 Warp、1 个调度 Warp 及 8 个 Epilogue/Combine Warp 竞争同一个 CTA 的寄存器文件、共享内存与指令发射槽。这种单核融合模式带来了三个核心痛点：

  1. 计算 Warp 无法独占整颗 SM：分发 Warp 及其暂存缓冲区被强行从每个 SM 的寄存器与共享内存中切分出去，拉低了单 SM 的 GEMM 吞吐。
  2. 全局同步域过大且存在尾部跨 Rank 栅栏：内核的序言（prologue）和尾部网格同步覆盖全卡所有 SM（B300 上为 148 个 SM），必须等待最慢的 CTA；且每次重放（replay）末尾在工作区清理后都需要一次跨 Rank 的 tag-2 栅栏（round trip）。
  3. 资源预算强耦合：所有阶段共享同一 CTA 的寄存器和共享内存预算，对任一阶段的局部优化（如更深的权重流水线或更轻量的分发路径）都会牵动整个内核的资源平衡与同步约束。

此外，低精度格式正向 FP8 激活 $\times$ FP4 权重演进（权重访存而非算术吞吐决定了 Decode 下界），且 Hopper 与 Blackwell 在混合 FP8 $\times$ FP4 计算上暴露了完全不同的指令集。而现有系统层重叠方案（跨 micro-batch、跨层、跨专家或普通多 CUDA Stream）要么无法缩短单层关键路径，要么无法在算子内部提供硬件级 SM 共驻与性能隔离保证。

1.2 研究目标与主要创新点

本文提出 GC-MoE，一个面向 NVIDIA Hopper（SM90）和 Blackwell（SM103）GPU 的开源 FP8/FP4 MoE 推理算子。其核心目标是在不牺牲数值精度的前提下，将 MoE 层重构为跨两个 CUDA Green Context（绿色上下文） 的三节点 CUDA Graph（Hopper 融合共享专家时为四节点），在驱动层将 GPU 静态划分为小型通信分区与大型计算分区，从而以硬件级 SM 隔离实现算子内部的通信与计算重叠。论文明确提出以下四项核心贡献：

  1. 面向 Decode 特征的绿色上下文分解（Decode-aware green-context decomposition）：据作者所知，GC-MoE 是首个利用 CUDA Green Context 为 Token 分发与专家计算分配互不相交、驱动对齐 SM 分区的 MoE 算子。分发与分组 GEMM 作为独立内核在专属 SM 上并发运行，而非在每颗 SM 内共享资源；通过启用均衡工作队列（balanced workqueues）避免两个上下文之间的隐式串行化。由于 Decode 阶段分组 GEMM 受限于显存带宽，划出 20 个 SM（B300 共 148 个 SM）给分发几乎不损失计算吞吐，且每个角色作为独立普通内核拥有各自的资源预算与同步域，使得分发与 GEMM 路径能够独立调优（见第 3 节与第 4.2 节）。
  2. 细粒度跨分区同步机制（Fine-grained cross-partition synchronization）：设计了带有代次标记（generation-tagged）的满/空计数器的 Token 环（token ring）以及 64 位 W1 完成位图（bitmap），将基线的块级（block-granular）握手协议跨越分区边界延续下来，使计算内核在第一个环形块填满时即可启动，无需等待分发全部完成；采用奇偶双缓冲（double-buffered）接收计数器消除了 CUDA Graph 重放之间的尾部跨 Rank 栅栏；所有同步状态均常驻设备端，无需主机干预即可跨重放持久化（见第 4.3 节与第 4.6 节）。
  3. 双架构 FP8 $\times$ FP4 分组 GEMM 实现（Dual-architecture FP8 $\times$ FP4 grouped GEMM）：在 Blackwell（SM103）上实现操作数交换的 tcgen05 块缩放（block-scaled）MMA 路径并配合 K128 瓦片预打包（tile-prepacked）FP4 权重，以单一指令序列同时服务 FP4 路由权重与 FP8 共享权重；在 Hopper（SM90）上实现寄存器-A（register-A）WGMMA 路径，结合寄存器内 FP4 到 E4M3 解码以及基于窗口的精确缩放因子重打包。两条路径均在第一阶段 GEMM Epilogue 中融合了 SwiGLU、路由权重乘积与 FP8 重量化，并支持可选的共享专家融合（见第 4.4 节与第 4.5 节）。
  4. 系统化跨代评估与开源实现（Systematic evaluation）：在 $8 \times \text{H20}$ 与 $8 \times \text{B300}$ 平台上共 54 个实测 Decode 数据点上，GC-MoE 全部超越 DeepGEMM Mega MoE（其中 H20 共享专家的 9 个数据点对比非融合共享专家基线）：在 H20 上针对 DeepSeek-V4.1-Flash 平均加速 $1.188\times$（路由专家与共享专家套件峰值分别达 $1.296\times$ 和 $1.353\times$）；在 B300 上针对 GLM-5.2 与 DeepSeek-V4.1-Flash，无共享专家平均加速 $1.106\times$，融合共享专家平均加速 $1.123\times$（峰值 $1.209\times$）。数值精度与基线严格匹配：所有测试点相对 BF16 参考的余弦相似度 $\ge 0.97$，H20 两套基准相对基线的最小余弦相似度 $\ge 0.9999997$（见第 6.3 节与第 6.5 节）。该算子已完整开源。

二、背景知识

符号约定：论文中以 $P$ 表示 Rank（GPU）数量，$E$ 表示路由专家总数，$e = E / P$ 表示每个 Rank 持有的本地专家数，$H$ 表示隐藏层维度（hidden size），$I$ 表示中间层维度（intermediate size），$T$ 表示每个 Rank 的 Token 数量，$k$ 表示 top-$k$ 路由因子。$B_M$ 表示分组 GEMM 的 Token 块大小；在 Blackwell 路径上，$B_N = 128$ 与 $B_K = 128$ 为固定的 MMA 瓦片维度。文中 FP8 指 E4M3 格式，FP4 指按每字节打包两个值的 E2M1 格式，UE8M0 指微缩放（microscaling）配方中使用的无符号 2 的幂次指数缩放因子。

2.1 专家并行下的 MoE 层

MoE 层数学表达与四阶段分解：在专家并行下，路由专家 MoE 层对单个 Token $t$ 的计算公式为：

$$ y_t = \sum_{j \in \mathrm{TopK}(t)} g_{t,j} W_2^{(j)} \mathrm{SwiGLU}\Bigl(W_1^{(j)} x_t\Bigr) + \underbrace{W_2^s \mathrm{SwiGLU}(W_1^s x_t)}_{\text{可选共享专家}} $$

其中，$W_1^{(j)} \in \mathbb{R}^{2I \times H}$ 堆叠了门控（gate）与上投影（up）权重，$W_2^{(j)} \in \mathbb{R}^{H \times I}$ 为下投影（down）权重，$g_{t,j}$ 为路由权重。在专家并行下，$E$ 个专家均匀切分至 $P$ 个 Rank，每个 Rank 执行 $e = E / P$ 个本地专家。因此，单层 MoE 执行可分解为四个阶段：(i) 分发（dispatch），即一次全对全数据交换，将每个 Token、其激活缩放因子以及路由元数据发送至拥有其所选专家的 Rank；(ii) 第一阶段分组 GEMM（Grouped GEMM 1），针对每个专家的 Token 分组进行计算，并在 Epilogue 中融合 SwiGLU；(iii) 第二阶段分组 GEMM（Grouped GEMM 2），生成下投影结果；(iv) 聚合（combine），将 $k$ 个部分输出按权重规约回源 Rank。在数据精度格式方面，Blackwell 路径的路由激活采用 FP8 格式并沿归约维度每 32 个数值配备一个 UE8M0 缩放因子，路由权重采用同样 32 值缩放粒度的 FP4 格式，共享专家权重采用 FP8 格式；而 Hopper 路径则消费带有连续 FP32 K128 缩放因子的 E4M3FN 激活（详见第 2.3 节与表 2）。

小批量 Decode 阶段的瓶颈特征：在小批量 Decode 场景下，每个 Rank 仅拥有 1–256 个 Token，导致每个本地专家接收到的 Token 极少，单专家 GEMM 的 $M$ 维度非常小（分组后往往只有 16–32 行）。以 GLM-5.2 的 256 专家、8 Rank、top-8 配置为例，在负载均衡路由下，每个专家平均分得的 Token 数为 $T \cdot k \cdot P / E = T / 4$；当每个 Rank 仅有 1 个 Token 时，每个专家平均仅收到 0.25 个 Token，填充后的 $M$ 瓦片几乎全为填充值（padding）。此时，分组 GEMM 完全受限于显存带宽（bandwidth-bound）：其主要耗时来自于从 HBM 流式加载本地 FP4 专家权重及缩放元数据，而非算术运算。与此同时，分发阶段受限于延迟（latency-bound）：其关键路径为跨 Rank 数据交换加上对等端原子计数（peer-atomic accounting），且只需极少数 SM 即可打满 NVLink 带宽。由于带宽受限的 GEMM 从额外 SM 中获益甚微，整个 MoE 层并不需要全卡 SM 参与算术计算；然而，单个融合内核会横跨所有 SM，当 MoE 层本身执行时间很短时，全卡同步域的开销显得尤为昂贵。上述三项观察——分发需要 SM 但不需要 Tensor Core、Decode 分组 GEMM 需要 Tensor Core 但受限于带宽、以及全 SM 同步在 Decode 阶段代价高昂——构成了本文工作的根本前提。

2.2 GPU 执行模型：Hopper、Blackwell、Green Contexts 与 CUDA Graphs

Hopper（SM90）执行特性：在 H20 上，内核编译目标为 sm_90a。该架构提供线程组矩阵乘累加（Warpgroup MMA, WGMMA）、异步 TMA（Tensor Memory Accelerator）拷贝以及 Warp 专业化（warp specialization）机制；由四个 Warp 组成的 Warpgroup 发射 wgmma.mma_async 指令，其操作数可来自共享内存或寄存器。但 Hopper 缺乏原生 FP4 MMA 硬件支持，FP4 权重在送入 Tensor Core 之前必须通过软件解码为 E4M3 格式。

Blackwell（SM103）执行特性：在 B300（计算能力 10.3，属于具备 148 个 SM 的 SM100 家族芯片）上，内核编译目标为 sm_103f。第五代 Tensor Core 通过 tcgen05 指令集编程：MMA 的累加结果驻留在张量内存（Tensor Memory, TMEM）中，由两个 CTA 组成的集群对（two-CTA cluster pair）可协同发射单条 MMA 指令（cta_group::2），且块缩放变体 kind::mxf8f6f4.block_scale 利用硬件缩放因子按每 32 个数值一组对混合 FP8/FP4 操作数执行乘法。MMA 的完成通过 mbarrier 发出信号，随后使用 tcgen05.ld 从 TMEM 读回结果，从而使 Epilogue 能够与下一次 MMA 进行软件流水线重叠，无需全设备级栅栏同步。

CUDA Green Contexts 机制：绿色上下文（Green Context）是一种轻量级执行上下文，仅拥有设备中全部 SM 的一个子集。CUDA 驱动 API 暴露了查询设备 SM 资源（cuDeviceGetDevResource）、按数量切分 SM 资源（cuDevSmResourceSplitByCount）以及基于切分结果创建绿色上下文（cuGreenCtxCreate）的接口。提交到绿色上下文关联流（stream）中的内核只会被调度到该上下文所拥有的 SM 上执行；因此，两个绿色上下文可以在互不相交的 SM 集合上并发运行，既不需要 MPS 守护进程，也不需要进程级配置。切分的粒度与对齐方式由驱动属性决定（包括最小分区尺寸与共调度对齐单位），因此应用程序提出分区大小请求后，由驱动确定最终可用的分区规模。此外，绿色上下文还可携带工作队列（workqueue）配置：采用均衡共享作用域（balanced sharing scope）且并发上限设为 1 时，每个上下文将分配到独立的硬件工作队列，从而避免两个上下文的内核因争抢同一队列而发生隐式串行化。

CUDA Graphs 机制：CUDA Graph 将内核节点组成的有向无环图（DAG）捕获一次，之后可以极低的主机端开销反复重放。图中没有依赖边的独立节点具备并发执行资格；同时，节点参数在捕获时固定并可按值传递（pass by value），这使得图能够直接携带大型描述符表（如张量映射 Tensor Map、对等地址表），避免了每次启动时的指针追踪开销。GC-MoE 正是利用这些特性，将 MoE 算子表达为一个可附加到外部捕获图中的三节点子图（详见第 4.6 节）。

2.3 低精度数据格式

Blackwell 与 Hopper 的量化格式及缩放配方：在 Blackwell 路径上，算子接收由调用方预先量化为 FP8 E4M3 格式的激活值，沿 $K$ 维度每 32 个连续值配备 1 个 UE8M0 缩放因子，并将 4 个指数（exponent）字节打包进 1 个 int32 中。路由权重为同样具备 K32 微缩放粒度的 FP4（E2M1）格式，每字节打包两个数值；共享专家权重为 FP8 格式。这就是 $(1, 1, 32)$ 配方：两个操作数均为每 $1 \times 32$ 数值块对应 1 个缩放因子。针对共享专家，GC-MoE 还额外支持 $(1, 128, 128)$ 配方，其权重缩放因子覆盖 $128 \times 128$ 块；在该配方下，调用方在权重变换前会将块行缩放因子展开为每个输出行对应一个打包行。上述 FP4 格式及其缩放约定与 NVFP4/MXFP4 风格的训练和推理工作一致【[20] Pretraining large language models with NVFP4, 2025, arXiv:2509.25149；[28] Training LLMs with MXFP4, 2025, arXiv:2502.20586】。在 Hopper 路径上，激活使用带有连续 FP32 K128 缩放因子的 E4M3FN 格式，而路由权重遵循 MXFP4 约定（E2M1 配合 UE8M0 K32 缩放因子）。需要指出的是，GC-MoE 的权重变换仅重新排布已经量化好的数据与缩放因子，绝不执行浮点权重的量化操作。

三、基线瓶颈分析与设计原则

DeepGEMM Mega MoE 的执行模型与关键路径：如图 1(a) 所示，DeepGEMM 的 Mega MoE 在 B300 上以单个持久化融合内核占据全部 148 个 SM 来执行一层 Decode 计算。通过 Warp 专业化，每个 CTA 分配了 4 个分发 Warp（128 个线程）、4 个非 Epilogue Warp（包括 2 个 TMA 加载 Warp、1 个 MMA 发射 Warp 和 1 个调度 Warp，后两者仅在每个 2-CTA 集群的主 CTA 中运行）以及 8 个同时负责 Combine 的 Epilogue Warp（256 个线程）。内核启动后先进行路由计数并执行一次 tag-1 跨 Rank 栅栏同步，随后进入流式阶段：分发 Warp 将 Token、缩放因子及路由元数据拉取至每块（per-block）Token 环中，而 GEMM 一旦检测到某个环块填满便立即消费它。因此，分发与计算确实存在重叠，但这种重叠发生在相同的 SM 上，属于空间共享（spatial sharing）：分发 Warp 及其暂存缓冲区被硬生生从每个 SM 的寄存器文件和共享内存中切走，拉取操作仅由每个 SM 内的 4 个 Warp 发起；且内核末尾在工作区清理之后还需要执行一次 tag-2 跨 Rank 栅栏，所有 Rank 必须通过该栅栏后，下一次重放才能安全复用工作区。虽然清理操作显式地与 Combine 规约重叠，但 tag-2 栅栏紧随清理之后，是一次必须支付的跨 Rank 往返通信。其关键路径可建模为：

$$ T_{\mathrm{mega}} = t_{\mathrm{pro}} + \max\left(T_{\mathrm{pull}}^{\mathrm{shared}}, T_{\mathrm{gemm}}^{\mathrm{shared}}\right) + \max\left(T_{\mathrm{combine}}, t_{\mathrm{clean}} + t_{\mathrm{tag2}}\right) $$

其中，$t_{\mathrm{pro}}$ 表示序言耗时，中间两项在同一套共享 SM 阵列上并发执行，而尾部耗时取最终 Combine 耗时与“工作区清理加 tag-2 栅栏耗时”两者的较大值。

单核融合模式的三大固有开销：由上述执行模型直接衍生出三项性能与工程代价。第一，计算 Warp 永远无法独占整颗 SM，因此单 SM 的 GEMM 吞吐低于专用 SM 所能达到的水平。第二，同步域覆盖整个设备：序言和尾部的网格同步囊括全部 148 个 SM，导致每个阶段都必须等待最慢的那个 CTA；且 tag-2 栅栏在每次重放中都会引入一次跨 Rank 往返延迟，只有当 Combine 本身耗时超过“清理 + 栅栏”时，这部分开销才能被隐藏。第三，融合导致各阶段的资源预算高度耦合：所有角色必须挤在同一个 CTA 的 64,512 个寄存器与 227 KB 共享内存中，即便是处于空闲状态的角色也依然占据着其保留份额；因此，无论是加深权重流水线、扩大 Epilogue 规模还是优化分发路径，都必须满足合并后的总预算，并且不能破坏其他所有角色的栅栏与缓冲区布局，任何局部优化都要由整个内核来买单。

GC-MoE 的解耦优势与性能收益来源：GC-MoE 一举消除了上述全部三项开销。其中，role1 在 20-SM 通信上下文中执行分发并独占这 20 颗 SM 的全部资源用于拉取；role2 在 128-SM 计算上下文中执行分组 GEMM 且不背负任何分发 Warp；role3 的收尾（finalize）网格规模则更小。由此，围绕跨 Rank tag-1 栅栏的网格同步仅跨越 20 个分发 SM，role3 的网格同步仅跨越其收尾网格，而非全部 148 个 SM。同时，基于奇偶双缓冲的接收计数器使 role3 只需翻转代次标志，彻底免除了等待 tag-2 栅栏的必要。由于各角色现为独立内核，每个角色均拥有专属的线程数、寄存器、共享内存和同步预算：分发路径可以专门面向低延迟调优，GEMM 路径可以专门面向权重流式传输与 MMA 吞吐调优，无需反复权衡共享 CTA 的资源分配，各角色还能独立引入面向特定阶段的优化。在此基础上，GC-MoE 还通过将 FP4 权重预打包为 K128 瓦片进一步提升了 GEMM 本身的性能（第 4.4 节）。在实测的 H20 配置上，GC-MoE 在每 Rank 4–32 个 Token 区间将端到端延迟降低了 20.9%–22.8%（加速 $1.26\text{–}1.30\times$）——正是在这一区间内，小 $M$ 下的分组 GEMM 仍受限于发射延迟，共享 SM 的惩罚与 tag-2 栅栏对短关键路径的影响最重；而在每 Rank 256 个 Token 时，权重流式读取主导了整层耗时，两类算子均逼近流式带宽极限，此时相对收益收缩为大致固定的共享 SM 节省与尾部开销节省（第 6.2 节）。

三种替代方案的局限性：作者剖析了三种直觉上的替代方案为何无法解决上述问题。(i) 无隔离的多 CUDA Stream 并发：在全设备启动的常规内核会填满所有 SM，并发启动的通信内核只能排队等待或从计算内核中抢占 SM，既没有硬件级共驻保证，也无法免受占用率（occupancy）干扰。(ii) 单融合内核配合 Warp 专业化（即基线方案）：分发与计算虽能重叠，但只能通过共享每颗 SM 实现，因为单个内核在不排空流水线的情况下无法在不同角色间重新划分 SM；分发 Warp 及其暂存缓冲从每颗 SM 预算中割肉，拉取仅靠寥寥几个 Warp 驱动，且调用间仍需尾部跨 Rank 栅栏保护工作区复用；同时 CTA 的寄存器和共享内存预算已被锁死，孤立地优化某一阶段极为困难。(iii) 跨 micro-batch 或跨层的软件级流水重叠：这类方案虽能用其他工作隐藏通信耗时，但无法缩短单个 MoE 层本身的关键路径延迟，并且会改变模型的数值调度顺序。

GC-MoE 的五项核心设计原则：基于上述分析，GC-MoE 确立了五项设计原则。第一，静态但原生的 SM 硬件划分：利用驱动层的 Green Context SM 切分机制，使分发内核与计算内核在互不相交的 SM 集合上共驻，获得硬件级隔离。第二，独立内核化的角色预算：将每个角色实现为普通内核，各自拥有独立的线程、寄存器、共享内存与同步预算，从而解耦分发调优与 GEMM 调优，避免像融合基线那样将每次局部改动计入单一 CTA 的总预算。第三，跨分区边界的细粒度环形握手：将基线的块级 Token 环握手协议延伸至分区边界两侧，让计算内核在首个环块填满后即刻启动，而无需等到分发结束。第四，设备常驻同步与双缓冲去尾部栅栏：所有同步状态常驻设备端并跨 CUDA Graph 重放持久化，同时对跨 Rank 计数器进行双缓冲，从而彻底消除重放间的尾部栅栏。第五，面向架构特化的计算内核：鉴于 Hopper 与 Blackwell 在混合 FP8 $\times$ FP4 计算指令集上存在本质差异，分别为两代架构定制专属计算内核。

图 1 验证了时间线结构对比：图 1(a) 展示了 B300 上 DeepGEMM Mega MoE 在全部 148 SM 上重叠执行分发与计算但受限于共享 SM 资源及尾部 $\max(T_{\mathrm{combine}}, t_{\mathrm{clean}} + t_{\mathrm{tag2}})$ 往返延迟；图 1(b) 展示了 GC-MoE 将 role1 隔离至 20 SM、role2/role3 置于 128 SM，通过虚线触发信号在首个环块就绪后立即启动 role2，并移除 tag-2 栅栏，使下一次重放在 role3 结束后即可无缝衔接（绿色区域）。实测端到端加速比在路由专家扫描中达 $1.03\text{–}1.30\times$，含共享专家时达 $1.01\text{–}1.35\times$（见第 6.2 节）。

四、GC-MoE 架构与方法设计

4.1 总体架构概述

三节点子图与角色职责划分：GC-MoE 将单层 MoE 的执行组织为一次包含三个内核节点（称为角色，role）的子 CUDA Graph 重放（见表 1 与图 2）。其中，role1（dispatch）运行在通信绿色上下文上，负责路由计数以及将数据通过全对全拉取（all-to-all pull）写入本地 Token 环；role2（compute）运行在计算绿色上下文上，负责执行路由专家与共享专家的分组 GEMM（融合 SwiGLU 与重量化），并将 BF16 部分输出直接分散写（scatter）回源 Rank；role3（finalize）运行在计算绿色上下文上，负责将式 (1) 中的 $k$ 个（加上可选的 1 个共享专家）部分输出规约为最终输出。role1 与 role2 是该 CUDA Graph 中互无依赖边的并发根节点（图 2 中并排绘制），因此驱动能够将二者同时调度到互不相交的 SM 集合上执行；role3 则同时依赖于 role1 与 role2。每个角色都是一个普通内核，拥有各自的启动边界（launch bounds）、寄存器和共享内存占用以及同步域，角色间不共享任何 CTA 预算。正是这种架构解耦，使得 role1 可针对通信延迟优化，role2 可针对权重流式读取与 MMA 吞吐优化，且任一路径的修改均不会扰动其他路径。算法 1 概括了单次重放的完整流程。

对称内存布局与跨 Rank 寻址机制：所有跨 Rank 数据——包括输入激活、路由表、Token 环、Combine 缓冲区以及全部同步信号——均驻留在同一块对称内存（symmetric-memory）分配空间内，该空间通过 PyTorch 的分布式对称内存 API 创建并在所有 Rank 间完成会合（rendezvous）。每个 Rank 均获取其余所有 Rank 对称内存分配的对等虚拟地址（peer virtual address）并传入内核；具体而言，一个 592 字节的按值传递描述符携带了本地基址与 72 个相对偏移量，内核仅需加上一个有符号增量（signed delta）即可映射到任意对等 Rank 的内存基址。各个内核正是通过这些对等地址经由 NVLink 发布并消费逐专家计数器、环形计数器以及 Combine 就绪信号。

4.2 基于 Green Context 的 SM 静态划分

运行时创建流程与均衡工作队列验证：运行时会为每个 CUDA 上下文创建一对绿色上下文并进行缓存（见图 2），创建流程严格包含以下四个步骤：(1) 查询设备的 SM 资源属性，获取设备总 SM 数、最小分区尺寸以及共调度对齐粒度（co-scheduling alignment）。(2) 将目标计算分区 SM 数量计算为 $\lfloor (\text{total} - \text{requested}) / \text{alignment} \rfloor \cdot \text{alignment}$，其中 requested 为应用程序的分发 SM 请求量（由环境变量 GC_MOE_DISPATCH_SMS 指定，默认值为 16），随后调用 cuDevSmResourceSplitByCount 切分 SM 资源，驱动返回计算分区资源及其互补的通信分区资源。因此，最终分区是由驱动对齐而非应用任意指定的：在拥有 148 个 SM 的 B300 上，默认请求 16 个分发 SM 经驱动对齐后得到 20/128 的通信/计算切分。(3) 当启用均衡工作队列（默认开启）时，从主上下文获取工作队列配置资源，设置 sharingScope = CU_WORKQUEUE_SCOPE_GREEN_CTX_BALANCED 且 wqConcurrencyLimit = 1，利用 SM 资源与工作队列资源共同生成上下文描述符；创建完毕后，运行时会回读该资源以验证均衡并发限制确实生效。均衡工作队列在工程实践中至关重要：若不启用，两个绿色上下文可能被映射到同一个硬件工作队列上，从而静默地将原本意图并发重叠的两个内核串行化。(4) 为每个上下文创建一个非阻塞绿色流（non-blocking green stream）及一个退役事件（retirement event）；销毁阶段先记录事件、同步等待完成后再销毁上下文。该绿色上下文对按 CUDA 上下文进行线程局部缓存，并在运行时强制校验合法性：计算分区至少包含 32 个 SM 且数量为偶数，分发分区至少包含 2 个 SM，且两者 SM 数量之和必须等于设备总 SM 数。

静态划分的确定性与极低代价：该划分策略带来了两个值得强调的直接后果。首先，分区在 CUDA Graph 的整个生命周期内保持静态，确保了图重放的完全确定性：内核永远不会被迁移，分发分区的 SM 数量成为所启动内核的编译期常量属性。其次，在 Decode 这一目标工作区间内，切分带来的计算资源让渡代价微乎其微：虽然 B300 将 148 个 SM 中的 20 个（占 13.5%）划给了分发、仅留 128 个给计算，但在 Decode 批量下分组 GEMM 受限于权重流式传输与小 $M$ 发射延迟而非 Tensor Core 算力，128 个 SM 已完全够用；实测有效吞吐证实，更小的专用计算分区依然全面超越基线的 148-SM 共享内核（见第 6.2 节）。此外，分区还大幅收缩了同步域：role1 的网格同步（包括 tag-1 栅栏前后的同步）仅覆盖 20 个分发 SM，role3 的网格同步仅覆盖其收尾网格（每 Rank $\le 128$ Token 时为 64 个 SM），计算分区的任务调度器也仅局限于自身的 128 个 SM，而基线的序言与尾部网格同步却不得不涵盖全部 148 个 SM。

4.3 分发与专家计算的重叠机制

全局复用 Token 环与容量模型：分发阶段不为每个专家单独分配缓冲区，所有拉取过来的 Token 统一落入一个全局复用的 Token 环中，环由大小为 $B_M$ 个 Token 的环块（ring block）组成。每个环块携带四个持久化信号：l1_full_count（由分发内核在环块填满时发布）、l1_empty_count（由计算内核在环块激活消费完毕后释放）、l2_full_mask（记录已完成 W1 输出瓦片的 64 位位图）以及 l2_empty_count（在环块的 L2 激活消费完毕后释放）。环容量依据最大在途（maximum-in-flight）模型严格推导：在单 Rank 容量上限为 $T_{\max}$ 时，最大路由分配数为 $T_{\max} \cdot P \cdot \min(k, e)$，逻辑块池规模为 $\lceil \text{assignments} / B_M \rceil + e$，而同时存活的块数则根据实际计算分区的 SM 数量以及 L1/L2 集群波次（cluster waves）重新计算。由于容量检查直接使用真实的分区大小，CUDA Graph 绝不会在环空间不足的情况下启动。因为环块会跨代次循环复用，每个逻辑池块都会映射到一个物理环块编号加一个代次号（generation number）；分发内核在覆盖某一环块前，必须观测到消费者已释放上一代次（通过 l1_empty_count）。代次标记保证了单次重放内部跨代次块复用的安全性；而在两次重放之间，role3 会在内核内部与 Combine 一半并发地重置环信号（见第 4.6 节），因此不需要额外的独立重置阶段。

块级生产者—消费者握手与位图依赖：计算内核的 TMA 生产者 Warp 以 acquire 内存语义等待目标环块的 l1_full_count 达到 $B_M \cdot (\text{generation} + 1)$，一旦条件满足便立即发布该环块的 W1 任务。因此，跨分区握手的粒度精确到单个环块：分组 GEMM 在第一个环块填满时便立刻启动，而不必等待整个分发过程完成。在单个环块内部，L2 阶段同样无需独立栅栏：每个 W2 的 K128 瓦片恰好消费两个 W1 的 N128 输出瓦片，W1 的 Epilogue 完成后会置位 64 位 l2_full_mask 中对应的位，L2 生产者只需精准等待其所需的两位被置位即可。由于该位图为每个 W1 N128 瓦片保留 1 个比特位，这也直接确立了 $2I / 128 \le 64$ 这一硬性设计约束（详见附录 A）。

集群调度器与任务派发策略：每个 2-CTA 集群的主 CTA 均运行一个调度器 Warp。计算任务按块划分为四个阶段类型：Linear1、Linear2、SharedLinear1 和 SharedLinear2。调度器先根据前述环容量模型预先发布少量 L1 波次，再发布首个 L2 波次，随后严格维持“一进一出（one-in-one-out）”纪律：每当成功认领一个 L2 任务时，便再发布一个新的 L1 任务；且某个池块的 L2 任务必须在该池块的所有 L1 任务发布之后才会被发布。对于共享专家任务，当其计算量较小时会插入到路由专家 L2 工作之前（与路由任务交错执行），而当其计算量较大时则排在路由任务之后。任务记录被封装为 32 字节描述符，借助分布式共享内存（distributed shared memory）配合事务计数 mbarrier 和双缓冲机制，广播给集群内的两个 CTA。

分发内核（Role1）六步数据通路：role1 按以下六个步骤顺序执行：

  1. 文件级/块级 Token 计数：每个 Warp 每次迭代处理 $32 / k$ 个 Token，并在共享内存中累加每个专家的本地 Token 计数。
  2. 打包原子计数更新：向本地逐专家发送计数器执行一次打包原子加操作 (1 << 32) | count，其中高 32 位记录贡献者 (rank, dispatch-SM) 的数量用于到达校验，低 32 位累加 Token 总数。
  3. 对等路由索引写入：进行第二遍扫描，将每个 Token 的路由条目通过跨卡对等写（peer write）写入目标 Rank 的源索引区域（source-index region）。
  4. 计数与前缀和发布：执行一次分发网格内同步后，由 block 0 将逐专家计数和前缀和发布至每个对等 Rank 的接收计数器中。
  5. 两阶段 NVLink 栅栏（tag 1）：确保所有对等端的计数在拉取开始前全部可见；该栅栏是一个能够跨越图重放的持久化、带阶段编码的计数器，且配备可配置的超时保护（默认 3600 秒），超时后触发设备陷阱（trap）而非无限死锁。
  6. 全局游标拉取与布局重排：每个 Warp 使用全局游标遍历按专家拼接且未填充的 Token 序列，借助线程泳道（lane）持有的逐 Rank 计数寄存器与 Warp 规约定位每个 Token 的 (src_rank, src_slot)；随后利用 Warp 私有的双缓冲共享内存暂存区，从对等端分块批量拷贝 FP8 激活及其对应的打包缩放因子行，并将其置换为 MMA 路径所需的 MN-major 行序；同时并排写入路由权重与 (src_rank, src_token, slot) 元数据，在环块的最后一个 Token 落地后释放该环块的 l1_full_count。

奇偶双缓冲消除尾部栅栏：早期架构（包括 DeepGEMM Mega MoE 至今）在每次内核调用末尾、工作区清理之后都必须执行第二次 NVLink 栅栏（tag-2），以确保下一次重放可以安全复用接收计数器与工作区。GC-MoE 改为对逐专家接收计数器实施按奇偶性双缓冲（double-buffered by parity）：单次重放消费代次为 $N \bmod 2$ 的计数器，而 role3 在消费完计数并完成自身网格同步后翻转奇偶标志（recv_parity），使下一次发布自动写入另一代次缓冲。跨重放的全局内存序由 tag-1 栅栏以及 Combine 就绪信号上的 release/acquire 链共同保证，完全不需要尾部跨 Rank 栅栏，从而从重放间关键路径上直接砍掉了一次完整的 NVLink 往返通信延迟。

W2 Epilogue 直接分散写入：W2 的 Epilogue 并不把中间结果先写入本地缓冲区再交由后续 Combine 内核搬运，而是由每个线程泳道直接发起 16 字节存储指令，将 BF16 数据片段跨卡分散写（direct scatter）到源 Rank 的 Combine 缓冲区对应的 (topk_slot, src_token) 槽位中；缓冲区的回收复用由 l1_empty/l2_empty 握手协议管控。由此，最终的 Combine 内核只需专注于规约计算，省去了从本地暂存区收集数据的开销。

4.4 双架构 FP8 $\times$ FP4 分组 GEMM

Blackwell（SM103）路径与指令调度：在 B300 上，GC-MoE 使用 2-CTA 块缩放 MMA 指令 tcgen05.mma.cta_group::2.kind::mxf8f6f4.block_scale：集群内的两个 CTA 协同发射一条 MMA 指令，其 FP32 累加器驻留在 TMEM 中，待 MMA 完成 mbarrier 触发后通过 tcgen05.ld 读回。与基线一致，算子采用操作数交换策略（operand-swapped）：指令的 A 操作数为权重瓦片，B 操作数为激活瓦片，因此 MMA 的 $N$ 维度对应 Token 维度。指令的 $N$ 尺寸设为该瓦片有效 Token 数向上取整至 16 的倍数，而非完整的填充块大小，使得未填满的环块付出成比例减少的计算代价。由于承载变化数据类型的是 A 操作数，同一套指令序列只需通过运行时选择的格式标识（format id），即可同时处理 FP4 路由权重（E2M1，format 5）与 FP8 共享专家权重（E4M3，format 0）；因为 CuTe DSL 公开的块缩放 MMA 接口要求 A/B 数据类型一致，GC-MoE 通过内联 PTX 用户自定义算子（inline-PTX user op）发射该指令。缩放因子通过专用的 UTCCP 路径搬运：在每个 K128 流水线阶段，激活缩放因子（$B_M$ 对齐行，每 16 字节包含 4 组打包 K32 因子）通过 tcgen05.cp.cta_group::2.32x128b.warpx4 拷贝至 TMEM（每阶段 512 字节），权重缩放因子走相同通路。随后每个 K128 阶段被拆分为 4 条 K32 MMA 发射，由缩放因子字节选择器挑出对应的 K32 组；针对 $(1, 128, 128)$ 共享专家配方，权重缩放因子每 4 个 K128 块仅暂存一次，选择器由 K128 块索引对 4 取模驱动。论文坦诚指出，Blackwell 路径的独特贡献并不在于底层的指令模式（操作数交换、有效 $M$ 驱动的 $N$ 缩放与 UTCCP 缩放通路均沿袭自基线），而在于围绕它的上层调度与布局革新：K128 瓦片预打包权重、统一共享专家任务流以及绿色上下文分区级重叠。

瓦片几何、TMEM 分配与形状约束：Blackwell 路径的瓦片几何固定为 $B_N = B_K = 128$，集群对中的两个 CTA 各负责一半的 $B_M$ 行。TMEM 分配量为 $2 B_M$ 列累加器空间加上由 $\lceil B_M / 128 \rceil$ 推导的缩放因子列数，向上取整到 2 的幂次且上限为 512 列。64 位 W1 完成位图限制了 W1 输出瓦片总数不得超过 64，即 $2I / 128 \le 64$；而每集群配对处理 N128 瓦片的机制则要求 $H / 128$ 必须为偶数（即 $H$ 为 256 的倍数）。

K128 瓦片连续权重预打包：权重变换将每个专家已量化的 FP4 矩阵从行优先的 [E, rows, K/2] 重排为 K128 瓦片连续布局 [E, k_b, rows, 64]：在单个瓦片内部，所有行的 64 字节数据段在显存中完全连续。配合编码了 (128, 128, 1, 1) 4 维盒子（对应 (K, rows, k_b, experts)）的 TMA 描述符，单次 TMA 操作即可突发传输一段 8 KB 的连续全局内存区域（FP8 共享权重为 16 KB），而不必像原先那样跨整行步长发起 128 次分散读取；同时，张量映射硬件会自动将 16U4 对齐存储的 FP4 负载解包为 8 位数据写入共享内存（SMEM）。门控（gate）与上投影（up）权重行按 8 行一组交错排布，使 SwiGLU Epilogue 能从同一瓦片中成对读取，缩放因子行亦置换为 UTCCP 消费顺序——这两点沿袭自基线权重变换，而 K128 瓦片连续预打包则是 GC-MoE 的新增优化，将分散的权重瓦片加载转化为单一连续突发访存。该变换在调用方流上异步执行，每套权重仅需运行一次，即可跨不同 Token 数、容量和图捕获反复复用。此外，路由 FP4 权重加载保留了基线的 EVICT_FIRST 缓存提示：Decode 每层仅流式读取一次权重，避免权重污染 L2 缓存可以保护激活与缩放因子的工作集。

W1 Epilogue 融合流水线：在 W1 Epilogue 中，累加器首先以 FP32 从 TMEM 读出，舍入为 BF16 并进行截断（clamp），接着计算 SwiGLU 的 sigmoid 项（可选用多项式指数与倒数实现 fast math），乘以上投影结果以及该 Token 的路由权重（提前在 W1 阶段应用路由权重，使 L2 GEMM 无需逐 Token 缩放），随后在 Warpgroup 内规约求取绝对值最大值（amax），转换为 UE8M0 缩放因子与 E4M3 数值负载，最后经由转置 stmatrix 写入 SMEM 并通过 TMA 存回 L2 激活环；重量化后的缩放因子行直接按照下一阶段 UTCCP 期望的置换顺序写出。当 $B_M = 240$ 时，Epilogue 采用寄存器双缓冲，使下一次存储对应的 TMEM 读取能够与当前批次的算术运算重叠。

$B_M$ 块大小启发式选择：主机端根据每专家期望 Token 数 $\hat{m} = T \cdot P \cdot k / E$ 及其标准差选取 $B_M$，目标是以最大候选块数覆盖 $\hat{m} + \sqrt{\hat{m}}$；候选集合为 $\{16, 32, 64, 96, 128, 192, 240\}$，小批量场景锁定 $B_M = 16\text{–}32$，当单 Rank 专家数较少时至少保证使用两个块，从而在 MMA 粒度与在途环块数量之间取得平衡。

Hopper（SM90）独立实现路径：SM90 算子是一套完全独立的实现，其激活为带连续 FP32 K128 缩放因子的 E4M3FN，路由权重为 MXFP4（E2M1 配合 UE8M0 K32 缩放因子），共享权重为 FP8。针对 Hopper 缺乏硬件块缩放 MMA 的短板，GC-MoE 引入了两大软件替代机制。第一，基于窗口的精确缩放因子重打包：主机端变换为每个专家根据其缩放因子极值计算窗口基准（window base，跨度至多 11 个指数步长），对于落出窗口范围的 FP4 幅值，通过覆盖 4 位编码空间的查找表按精确的 2 的幂次向下移位，并记录逐专家补偿因子；与此同时，将瓦片字节按寄存器解码器期望的泳道语义进行置换。第二，寄存器内 FP4 解码与外部块缩放：内核通过两条 LDS.128 加载指令结合 PRMT/LOP3 位操作在寄存器内将 FP4 实时解码为 E4M3，随后以 E4M3 操作数发射寄存器-A WGMMA m64nNk32 指令；块缩放因子在 MMA 之外以逐 K32 的融合乘加（FMA）形式施加，并对存储的缩放因子施加全局 $\times 64$ 约定，以将 E4M3 数值推入 WGMMA e4m3 的有效动态范围内。瓦片大小与 Warp 专业化由受 Token 数约束的启发式决定（$B_M \in \{8, 16, 32, 64\}$，在 384 线程流水线变体与 256 线程非流水线变体间选择），分发路径采用带对等表的纪元/计数器头（epoch/counter headers），默认请求 4 个分发 SM。表 2 系统总结了两条架构路径的差异。

4.5 融合共享专家设计

零拷贝激活复用与统一置换缩放暂存：共享专家作为可选功能直接融入同一任务流，而非作为独立层运行，其权重采用 K128 预打包的 FP8 瓦片。三项关键设计使得融合开销极低。首先，共享专家的 W1 GEMM 通过内存别名（aliasing）直接读取原始输入激活缓冲区（零拷贝）：由于共享专家作用于每一个本地 Token，因此无需经过分发阶段。其次，尽管共享权重可能采用不同配方，共享激活的缩放因子始终保持 K32 粒度，且必须呈现为与路由路径 UTCCP 消费格式完全一致的 MN-major 置换布局。调用方按每个 Token 数将其一次性暂存至 shared_l1_acts_sf：对于 Token $t$，令 $u = t \bmod B_M$，其目标行号严格定义为：

$$ \mathrm{row}(t) = \lfloor t / B_M \rfloor \cdot \mathrm{align}(B_M, 128) + \lfloor u / 128 \rfloor \cdot 128 + (u \bmod 32) \cdot 4 + \lfloor (u \bmod 128) / 32 \rfloor $$

式 (3) 所定义的行序与内核为路由激活缩放因子写入的行序分毫不差，从而让共享专家与路由专家复用同一套 TMA 缩放张量映射和同一条 UTCCP 通路；该暂存缓冲区容量为 $\lceil T_{\max} / 8 \rceil \cdot 128$ 行，这一上界对所有候选 $B_M$ 均有效，且该暂存操作可进一步融合进上游生产者（如量化算子）中。

统一调度流与无特例 Combine 规约：第三，共享专家任务以 SharedLinear1/SharedLinear2 阶段进入统一调度器，依据任务规模动态安插在路由专家工作之前或之后；其最终输出写入 Combine 缓冲区的第 $k$ 号泳道（lane $k$），使得 role3 的收尾内核在规约时无需任何分支特判即可自然汇总共享专家结果。在 SM90 路径上，共享专家则作为第四个独立图节点（role4）运行，并允许 role2 按需等待其完成。

4.6 三节点 CUDA Graph 聚合与重放

Role3 双半区并发执行：role3 是单个内核，但其内部划分为两个并发运行的半区（halves）。前 4 个 Warp 承担记账半区（bookkeeping half）：首先通过具备 release 语义的系统级原子操作向所有对等端发布 Combine 就绪信号（即便某 Rank 没有分配到任何路由 Token 也必须发布）；接着结合 dispatch_sms $\cdot P$ 的到达校验消费当前代次的逐专家接收计数，翻转 recv_parity；同时为下一次重放重置全部环信号、计数器以及 W1 完成位图，并顺带累加可选的逐专家接收统计信息。虽然 role3 依赖于两个图根节点并在 role2 完成后才启动，但记账半区并未引入额外的串行阶段：它与 Combine 半区并行推进，其重置工作在 Combine Warp 等待对等端就绪并执行规约的过程中同步完成。其余 Warp 承担聚合半区（combine half）：在带上限超时保护的前提下等待各对等端就绪，随后针对分配给当前分区的每个 Token 分块（chunk），利用双缓冲批量拷贝从（可能位于远程的）Combine 缓冲区预取并加载有效的 top-$k$（及共享）槽位数据，将 BF16 数值累加至 FP32 寄存器中，再成对打包回 BF16，经由 SMEM 通过批量 TMA 存储写出最终输出 $y$。分块几何（每个 Token 拆分为 1、2 或 4 个 chunk）根据可复用的 SMEM 预算并满足每泳道 16 字节对齐条件自动选择。

三节点图语义与无主机干预的图缓存重放：三节点 DAG 的构造具有明确的语义目的：role1 与 role2 之间无依赖边，从而确保驱动将两者并发调度到各自绿色上下文；role3 同时依赖两者，通过 release/acquire 就绪信号吸收了“所有 W2 部分和均已分散写完毕”的全局完成条件，避免了第二次跨 Rank 栅栏。更为关键的是，由于所有同步对象均为设备常驻且具备重放感知能力（包括栅栏阶段号、环代次号、接收奇偶位以及 Combine 就绪状态），每次 CUDA Graph 重放完全不需要主机侧执行任何状态重置。该子图既可通过捕获依赖语义（capture-dependency semantics）挂载到调用方的外层图捕获中，也可以在非捕获模式下直接作为独立图启动；运行时依据 cubin 哈希、参数签名与资源状态对子图进行缓存，从而使模型的多层重复结构及相同 Token 数请求能够直接复用已捕获的图实例。

五、系统实现

基于 CuTe DSL 的即时编译架构：GC-MoE 采用 Python 基于 NVIDIA CuTe DSL（CUTLASS DSL 4.8.1）编写，按配置即时编译（JIT）生成 PTX，再由系统汇编器（ptxas 13.2）编译为 cubin 二进制文件。整个算子以标准 Python 包形式分发，安装过程仅构建 wheel 而不预编译任何内核，内核编译延迟到首次使用特定配置时触发。

编译器标识绑定与两级缓存体系：为保证编译产物的确定性与安全性，GC-MoE 构建了一套严格的编译器标识记录（compiler-identity record），将 ptxas 路径、文件大小、版本号与哈希值、DSL 前端哈希、算子自身 Python 源码树的内容哈希、本地库标识以及有效编译选项全部绑定在一起。编译选项被锁定为 --gpu-arch <target> --opt-level 3，并对 ptxas 标志实施白名单管控（固定采用 -O3、寄存器使用级别 10 以及融合乘加），明确拒绝可重定位设备代码（relocatable device code）与用户任意覆写。在汇编器之上设有两级缓存：二进制缓存（binary cache）以编译器标识加内核属性、资源配置和张量元数据为键（绝不包含 CUDA 内存地址）；捕获键缓存（capture-key cache）则进一步按上下文、绿色分区以及所有指针/形状/超时参数索引张量映射编码和已加载内核。Cubin 通过 CUDA 驱动的库 API 加载并按哈希复用。

基于 PTX 后处理重写的按值内核参数：CUDA Graph 节点要求按值持有内核参数，这对 GC-MoE 尤为关键——计算内核需要携带 18 个张量映射（分别对应激活、缩放因子和权重的 TMA 描述符）以及完整的对等地址表，而 CuTe 默认会将两者均生成为指针形参。为此，GC-MoE 实现了一套 PTX 后生成重写器（post-generation PTX rewrite）：将对等描述符改写为 592 字节的按值 .b8 形参（包含基址、72 个 int64 偏移量及 Rank 索引），将每个张量映射改写为 128 字节对齐的按值形参，并通过 cvta.param.u64 重写所有 prefetch.tensormap 与 cp.async.bulk.tensor 指令中的参数空间地址；若生成的 PTX 结构发生变化，重写器将采用失效关闭（fail-closed）策略立即报错，并对参数顺序进行规范化以匹配图 ABI。SM90 路径共享上述 JIT 基础设施，并校验其专属 ABI（14 个指针加 3 个标量，且必须包含 wgmma.mma_async 与 cp.async.bulk 指令）。

分布式接口与极简调用范式：算子初始化要求每张 GPU 对应一个独立进程、GPU 间支持点对点访问（peer-accessible），并提供一个 PyTorch 分布式进程组。缓冲区 API 负责分配并在所有 Rank 间会合对称内存；权重变换 API 对每套权重仅需调用一次，返回变换后的权重对，可在图捕获之外于调用方流上异步执行；核心算子调用则将结果原地写入输出张量。代码清单 1 展示了 Blackwell 路径下路由专家的最小调用示例；启用融合共享专家时，仅需额外传入共享权重对及暂存后的缩放因子缓冲区。

6.5 数值精度验证

GC-MoE 直接复用调用方的量化输入与基线的量化权重，执行完全等价的低精度算术，差异仅源于调度、内存布局与指令选择。表 11 报告了 H20 路由专家精度测试套件的结果：涵盖 47 个用例（9 个默认、23 个边界、15 个含空 Rank 的非对称用例），跨越全部 8 个 Rank 共计 376 项检查。所有检查均通过余弦相似度阈值（相对 BF16 参考 $\ge 0.97$，GC 相对 Mega $\ge 0.97$），处理差异（processed difference，定义为 $1 - 2\langle y, \hat{y}\rangle / (\|y\|^2 + \|\hat{y}\|^2)$，对比将打包权重反量化后在 FP32 执行的参考前向）以及 Graph/Eager 重复性差异均满足 $\le 0.002$（重复差异严格为 0）。GC-MoE 相对基线的最小余弦相似度高达 0.9999998，且两者具有完全一致的最大绝对误差（0.109375）和最大相对 L2 误差（0.00600836286321），表明在 BF16 输出精度下两者共享同一误差包络。

高效算子内核与推理服务引擎：FlashAttention 确立了 IO 感知分块（IO-aware tiling）范式【[3] FlashAttention: Fast and memory-efficient exact attention with IO-awareness, 2022, NeurIPS】，其后续工作进一步挖掘并行度、Hopper 异步执行特性与 FP8 精度【[2] FlashAttention-2: Faster attention with better parallelism and work partitioning, 2023, arXiv:2307.08691；[25] FlashAttention-3: Fast and accurate attention with asynchrony and low-precision, 2024, arXiv:2407.08608】；Triton【[27] Triton: An intermediate language and compiler for tiled neural network computations, 2019, MAPL】与 CUTLASS【[22] CUTLASS: CUDA templates for linear algebra subroutines, Version 4.8.1, 2026b, https://github.com/NVIDIA/cutlass】则提供了分块内核编程基础设施 。DeepGEMM 提供了包含 Mega MoE 基线在内的 FP8/FP4 分组 GEMM 算子族，Mega MoE 已通过在每颗 SM 内共享资源并采用 Warp 专业化实现了分发与 GEMM 的重叠，而 GC-MoE 将这种共享 SM 组织重构为互不相交的 SM 分区【[7] DeepGEMM: A high-performance FP8 GEMM library for MoE and dense model inference, Version 2.8.2, 2026b, https://github.com/deepseek-ai/DeepGEMM】 ；FlashInfer 则贡献了面向推理的高效算子库【[9] FlashInfer: Kernel library for LLM serving, 2026, https://github.com/flashinfer-ai/flashinfer】。在推理服务引擎层，vLLM（PagedAttention） 【[16] Efficient memory management for large language model serving with PagedAttention, 2023, SOSP】与 SARATHI【[1] SARATHI: Efficient LLM inference by piggybacking decodes with chunked prefills, 2023, arXiv:2308.16369】等系统负责请求调度与显存管理，GC-MoE 则定位为可供此类引擎在 CUDA Graph 捕获下直接调用的底层算子。

低精度量化格式与微缩放实现：早期研究系统刻画了 FP8 格式及其缩放行为【[15] FP8 quantization: The power of the exponent, 2022, arXiv:2208.09225】，随后的 FP8 训练与推理栈确立了分组缩放（per-group scaling）范式【[23] FP8-LM: Training FP8 large language models, 2023, arXiv:2310.18313；[5] DeepSeek-V3 technical report, 2024b, arXiv:2412.19437】；NVFP4【[20] Pretraining large language models with NVFP4, 2025, arXiv:2509.25149】与 MXFP4【[28] Training LLMs with MXFP4, 2025, arXiv:2502.20586】则定义了本文所采用的 FP4 微缩放约定。GC-MoE 的贡献并非提出新的数值格式，而在于给出 FP8 $\times$ FP4 分组 GEMM 的双架构工程实现：在 Blackwell 上结合硬件块缩放、K128 权重预打包与分区级调度，在 Hopper 上则通过寄存器内 FP4 解码与基于窗口的精确缩放因子重打包落地（见第 4.4 节）。

GPU 空间划分与执行控制：CUDA Green Contexts 是驱动级的 SM 划分原语【[21] CUDA C++ programming guide (Green Contexts), 2026a, https://docs.nvidia.com/cuda/cuda-c-programming-guide/】， 而 MPS 与 MIG 提供的隔离粒度更粗。此前研究主要将 Green Contexts 与空间划分用于多任务隔离：例如评估 Green Contexts、MPS 与 MIG 的性能隔离特性【[19] Performance isolation for inference processes in edge GPU systems, 2026, arXiv:2601.07600】、在空间划分 GPU 上共置多个推理模型【[24] ECLIP: Energy-efficient and practical co-location of ML inference on spatially partitioned GPUs, 2025, arXiv:2506.12598】，以及在智能体推理服务系统中隔离 Prefill 与 Decode 槽位【[29] AgentServe: Algorithm-system co-design for efficient agentic AI serving on a consumer-grade GPU, 2026, arXiv:2603.10342】。据作者所知，GC-MoE 是首个将 Green Contexts 用于算子内部通信与计算重叠的工作，并实现了共驻内核之间以 Token 环块为粒度的细粒度同步。

八、结论、局限性与未来工作

核心结论：GC-MoE 将专家并行 MoE 层重构为跨越两个 CUDA Green Context 的三节点 CUDA Graph（Hopper 融合共享专家时为四节点）：小型通信分区持续将 Token 拉入环形缓冲区，大型计算分区即时消费已填满环块并执行 FP8 $\times$ FP4 Tensor Core 计算，收尾节点则在无尾部跨 Rank 栅栏的情况下完成规约输出。由于 Decode 阶段的分组 GEMM 受限于显存带宽，128-SM 计算分区让渡 20 个 SM 给分发几乎不损失有效算力，同时每个角色获得了独立的资源预算与同步域，实现了分发与 GEMM 的独立优化。除 SM 划分本身外，该设计依托三项核心要素——代次标记环形同步、奇偶双缓冲跨 Rank 计数器以及面向 Blackwell/Hopper 的双架构低精度 MMA 通路——最终在 $8 \times \text{H20}$ 上取得 $1.188\times$ 的平均 Decode 加速，在 $8 \times \text{B300}$ 上针对两款生产 MoE 模型取得 $1.106\text{–}1.123\times$ 的平均加速，且数值精度与基线在 BF16 精度下处于同一误差包络（H20 两套基准相对基线的最小余弦相似度 $\ge 0.9999997$）。

当前局限性：

  1. 适用负载边界：算子主要面向 Decode 阶段优化；尽管支持 Prefill 规模的大批量 Token，但此时计算分区算力（而非重叠）成为瓶颈，在实测最大批量（256 Token/Rank）处加速比收窄至 $1.01\text{–}1.13\times$。
  2. 硬编码形状约束：附录 A 所列约束源于底层硬性架构决策（64 位完成位图、静态信号区尺寸以及 72-Rank 按值对等表）。
  3. 消融实验范围有限：本版本未包含分区尺寸敏感性对照实验以及“开启/关闭重叠”的受控消融实验；文中仅报告了共享专家融合与非融合的算子内消融。
  4. 单实例工作区串行要求：由于对称内存工作区中的环与信号状态是持久化单实例，共享同一工作区的多次算子调用必须串行执行。

未来工作方向：作者计划开展针对分区规模与分发 SM 数量的系统化对照实验，将算子扩展至 Prefill 密集型场景及更多模型家族，在驱动支持更细粒度切分时探索自适应动态分区策略，并将 GC-MoE 深度集成至支持 CUDA Graph 捕获的生产级推理服务栈中。

$H \bmod 256 = 0$ 2-CTA 集群需要成对处理 N128 瓦片，因此要求 $H / 128$ 为偶数。
$k + \mathbf{1}[\text{shared}] \le 32$，且 $k \ge 1$ Warp 内单个线程泳道（lane）承载一个 Combine 槽位；且分发阶段每个 Warp 每次读取 $32 / k$ 个 Token。
全局 $E \le 2048$，单 Rank $\le 512$，且 $E \bmod P = 0$ 受限于静态逐专家信号区尺寸，以及线程泳道内持有的逐专家计数器容量。
$P \le 72$ Rank 592 字节按值传递的对等描述符固定容纳 72 个偏移量。
路由配方固定为 $(1, 1, 32)$；激活固定为 SwiGLU MMA 缩放因子通路硬编码支持 K32 UE8M0；SwiGLU 硬编码融合在 W1 Epilogue 中。
$B_M \in \{16, 32, 64, 96, 128, 192, 240\}$ 受限于 2-CTA MMA 对齐要求及 TMEM / SMEM 容量预算。
共享专家配方支持 $(1, 1, 32)$ 或 $(1, 128, 128)$ 缩放因子暂存与字节选择器逻辑仅针对这两种 $K$ 粒度实现。
单卡单进程，且 GPU 间需支持点对点访问（peer-accessible） 对称内存分配、Green Contexts 以及捕获图节点的跨卡直接访存前提。
同一工作区上的算子调用必须串行化 环形缓冲区与同步信号为持久化单实例状态。
